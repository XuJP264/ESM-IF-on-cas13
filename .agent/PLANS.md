# ExecPlan Standard

An ExecPlan is the authoritative, living implementation record for a major
feature or milestone. It must be understandable to a contributor who has only
the repository checkout and the plan itself.

## Required sections

Every ExecPlan contains:

1. **Purpose and evidence boundary** — the user-visible outcome and the highest
   evidence level the work can support.
2. **Current state** — what exists, what has been inspected, and known
   constraints.
3. **Milestones** — independently verifiable outcomes, not file-creation tasks.
4. **Progress** — timestamped checkboxes updated after meaningful work.
5. **Decisions** — choices, alternatives, and reasons.
6. **Discoveries** — unexpected behavior, measured machine constraints, and
   useful evidence.
7. **Execution details** — commands, working directories, expected outputs,
   seeds, and failure handling.
8. **Validation and acceptance** — tests and real-run criteria that demonstrate
   behavior.
9. **Artifacts and provenance** — paths to manifests, logs, run directories,
   reports, and hashes.
10. **Blockers and recovery** — exact blockers, evidence, and the next
    reproducible action.
11. **Outcomes and retrospective** — what is real, mock, not run, or deferred.

## Maintenance rules

- Create the plan before implementing a major feature.
- Keep exactly one step marked as active in the working plan when practical.
- Update progress during implementation, not retrospectively at the end.
- Record commands after they are actually run; do not write planned commands as
  successful evidence.
- Use UTC timestamps in machine records and include the local timezone in
  human-facing run summaries.
- When a milestone completes, update its ExecPlan, `docs/STATUS.md`, and
  `docs/DECISIONS.md` in the same coherent change.
- A milestone is complete only when its acceptance checks pass and resulting
  artifacts are inspectable.
- When an external dependency prevents a real run, complete safe independent
  interfaces and tests, record `not_run`, and preserve a one-command recovery
  route.
- If implementation diverges from the plan, update the plan before or together
  with the divergence and explain why.

## Result vocabulary

- `real`: generated by the declared production algorithm using genuine input
  and, where applicable, genuine model weights.
- `fixture`: deterministic small input used to test real code paths.
- `mock`: synthetic backend or prediction output; always `is_mock: true`.
- `not_run`: no result was produced; the reason and recovery command are
  mandatory.
- `failed`: execution began but did not satisfy its contract; logs and partial
  artifacts remain available.
